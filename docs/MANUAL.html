Manual de zeruel

Motor de orquestación de pipelines de datos en Rust. Un proceso por pipeline, techo de memoria por run, 49 MB en reposo.

Qué es y qué no

zeruel ejecuta pipelines de ETL: baja datos de algún lado, los transforma y los carga en otro. Decide qué corre y cuándo, se acuerda de lo que ya hizo, y no deja que un pipeline se coma la máquina.

Está pensado para servidores chicos. Un Airflow mínimo —scheduler, webserver, worker, Postgres y Redis— arranca en el orden de 1 a 2 GB antes de procesar un solo dato. zeruel en reposo son 49 MB, y un ETL de 10 millones de filas le entra en 833 MB.

Lo que no es:

  • No es un lenguaje de configuración. Los pipelines se escriben en Rust, no en YAML. Una transformación de datos no entra en un archivo de configuración sin inventar un mini-lenguaje, y ahí es donde se pierde el compilador, el autocompletado y la performance.
  • No es un cluster. Corre en una máquina. Si necesitás repartir trabajo entre varias, esto no es la herramienta.
  • No procesa en streaming continuo. Es por lotes: un run empieza, hace su trabajo y termina.

Instalar

Compilar

git clone <el repo> && cd zeruel
cargo build --release
# queda en target/release/zeruel

El binario completo pesa ~97 MB porque trae polars y wasmtime. Un pipeline que no usa dataframes pesa 3 MB: 32 veces menos, y ese es el que se copia al servidor por cada automatización.

Estructura en el servidor

/var/lib/zeruel/
├── state/          # base, WAL y logs. Lo unico que se escribe
│   ├── zeruel.db
│   └── logs/
└── pipelines/      # los binarios. Copiar uno aca alcanza
    ├── ventas.exe
    └── reportes.exe
Lo que más sorprende

Desplegar un pipeline nuevo es copiar un archivo. El scheduler re-escanea el directorio en cada tick y lo levanta sin reiniciar nada, sin recompilar zeruel, y sin interrumpir lo que esté corriendo.

Tu primer pipeline

Un crate propio que depende de zeruel:

# Cargo.toml
[dependencies]
zeruel = { version = "0.1", features = ["polars"] }
use zeruel::prelude::*;

struct Bajar;

impl Task for Bajar {
    fn id(&self) -> TaskId { TaskId("bajar".into()) }

    fn run(&self, ctx: &TaskContext) -> TaskResult {
        // ctx.param es el parametro del run: normalmente una fecha
        let datos = bajar_de_la_api(&ctx.param)?;
        Ok(TaskOutput::filas(datos.len()))
    }
}

fn main() -> zeruel::Result<()> {
    let dag = dag!("mi-etl",
        "bajar"   => [],
        "limpiar" => ["bajar"],
        "cargar"  => ["limpiar"],
    );

    pipeline(dag)
        .cron("0 4 * * *")
        .register(Bajar)
        .register(Limpiar)
        .register(Cargar)
        .start()
}

cargo build --release, copiás el binario a pipelines/, y ya está agendado.

Por qué el id sale del Task

register() no recibe el nombre: lo saca del propio Task. Si un id no coincide con el dag!, el pipeline falla al construirse, no a las 4 de la mañana cuando le toque correr.

La arquitectura

  pipelines/                 zeruel serve (scheduler)
    ventas.exe   ◄── lanza ── · lee la cola
    reportes.exe              · decide que corre (prioridad, RAM)
    inventario.exe                · NO ejecuta nada en su proceso
         │                              │
         └──────► state/zeruel.db ◄─────┘
                  (SQLite-WAL: la coordinacion)

Un proceso por run. El scheduler no ejecuta pipelines: los lanza como subprocesos. Eso da cuatro cosas que no se consiguen de otra forma:

  • Aislamiento real. Un panic o un exceso de memoria mata ese pipeline, no el scheduler ni los demás.
  • Despliegue por archivo. Copiar un binario, sin reiniciar.
  • Cada pipeline fija su propia versión de zeruel y de polars. No hay upgrade global forzado.
  • Las métricas de RAM son exactas. Con un proceso por run, el RSS del proceso es el del run: no hay que repartir nada entre hilos.

Lo que cuesta: 170 ms de arranque por run. Sobre un ETL de segundos o minutos es ruido; sería un problema sólo con tareas de milisegundos.

El contrato

El scheduler y cada pipeline se hablan por dos invocaciones. Las implementa la librería, así que quien escribe un pipeline no escribe nada de esto:

InvocaciónQué hace
<bin> --describe Imprime nombre, cron y grafo como JSON
<bin> run --param X --state DIR --run-id UUID Ejecuta y va guardando checkpoints

El JSON lleva zeruel_contract con la versión: 1 es un pipeline por binario, 2 permite varios. Se aceptan las dos, así que un binario viejo sigue andando sin recompilarlo.

Al actualizar zeruel

Cada pipeline lleva su propia copia de la librería compilada adentro. Si actualizás zeruel y algo del estado compartido cambió de nombre, el pipeline viejo escribe en un lado y el scheduler lee en otro: el run termina bien y aparece como fallido.

zeruel detecta ese caso y lo avisa con el remedio. La regla simple: al actualizar el scheduler, recompilá y volvé a copiar los pipelines.

La cola

Antes de lanzar algo, el scheduler pregunta cuatro cosas:

CriterioQué hace
PrioridadUn número. Más alto, primero.
Envejecimiento Lo que espera mucho sube solo. Sin esto, un item de prioridad baja nunca corre.
Conflicto No lanza dos runs del mismo DAG con el mismo parámetro a la vez.
Admisión por RAM No larga un run si su pico histórico no entra en la memoria libre.

La última es la que sorprende: podés ver items esperando con RAM aparentemente de sobra. Es deliberado — el scheduler se guarda margen para que el run que lance no termine haciendo swapear a la máquina.

El techo de memoria

Son dos, y se necesitan los dos:

  0 ──────────── techo blando ──── techo duro ────►
                 (2048 MB)         (2304 MB)
                 corta y dice      el sistema operativo
                 que tarea fue     rechaza la reserva

El blando mira el RSS cada 25 ms y corta con un diagnóstico completo: qué tarea, cuánto usó, cuál era el límite. El duro lo impone el sistema operativo un 12% más arriba, y existe para el caso que el muestreo no puede ver: una reserva de golpe entre dos muestras.

SistemaMecanismo
Linux, macOS, BSDsetrlimit(RLIMIT_DATA)
WindowsJob Object con ProcessMemoryLimit

Ninguno de los dos cuenta los archivos mapeados en memoria, que es justo la distinción que hace falta: un parquet de 10 GB mapeado no consume del techo, un Vec de 10 GB sí. 

zeruel serve --ram-max 2G     # para todos
zeruel run --ram-max 512M     # para uno suelto

El apagado ordenado

Cuando le piden parar, el scheduler hace tres cosas en orden:

  1. Deja de lanzar. Sale del bucle antes de tocar la cola.
  2. Espera a los runs en curso hasta --gracia-secs (30 por defecto).
  3. Lo que no llegó lo corta y lo devuelve a la cola.

Lo cortado se marca cancelado, no fallido: no falló nada, lo paró el operador. Y se reencola, porque "pararon el servicio" y "alguien canceló este trabajo" son cosas distintas, y sólo la segunda justifica perder el trabajo.

El número que hay que mirar

El plazo del supervisor tiene que ser mayor que --gracia-secs. Si mata el proceso antes de que termine el apagado, se pierde exactamente el trabajo que el apagado existe para no perder. Docker es el que muerde: su default son 10 segundos.

Los módulos

zeruel son seis crates. Están separados para que un pipeline pague sólo lo que usa: el árbol completo son 367 dependencias, y uno que sólo corre tareas de Rust se lleva 64.

zeruel-sdk

La API para declarar pipelines. Es lo único que toca quien escribe uno. 4 deps
Task
El trait que implementa cada tarea: un id() y un run().
TaskContext
Lo que recibe la tarea: el parámetro del run, el directorio de datos, y cancelled() para poder cortarse.
TaskOutput
Lo que devuelve: cuántas filas produjo, para que quede en las métricas.
Dag y la macro dag!
El grafo: qué tarea depende de cuál. Se valida al construirse, no al ejecutarse.

zeruel-core

El motor y la memoria. No lo usa directamente quien escribe pipelines. polars y wasm opcionales
Store
SQLite en modo WAL. Guarda runs, tareas, cola y agregados mensuales. Es también el canal de coordinación entre procesos: la orden de cancelar viaja por acá, así que se puede cancelar desde la web un run que lanzó el scheduler.
Engine
Ejecuta el DAG respetando dependencias, con reintentos y checkpoints. Si un run se reintenta, las tareas que ya terminaron no se repiten.
metrics
Muestrea RSS y CPU del proceso y todos sus descendientes cada 25 ms, redescubriendo el árbol cada medio segundo. Mide el árbol porque una tarea que envuelve un proceso externo —un script de Python, un dbt run— no gasta memoria en el wrapper de Rust: la gasta el hijo, y muchas veces el nieto. El CPU sale del contador acumulado del sistema, no de la diferencia entre muestras.
metricas
Las consultas de la pestaña Métricas. Se calculan sobre runs y task_runs con el recorte en el WHERE; rollups_monthly sólo aporta los meses cuyo detalle ya purgó la GC.
limite
El techo duro que impone el sistema operativo. Es lo único que se implementa distinto en cada plataforma.

zeruel-data

Transformaciones sobre dataframes y control de calidad. trae polars: +231 deps
PolarsTask
Una tarea que recibe un LazyFrame y devuelve otro. Trabaja en streaming: nunca materializa el resultado entero en memoria.
Chequeo
Reglas de calidad —cantidad de filas, columnas presentes, sin nulos, claves únicas, valores en rango— evaluadas todas en una sola pasada antes de cortar. Ver los cuatro fallos juntos evita el arreglo-recompilo-falla-el-siguiente.
ChequeoHistorico
Compara contra el promedio de las corridas anteriores. No sabe cuál es el valor correcto: sabe cuál es el habitual. Es lo que atrapa un +50% que ninguna regla fija habría marcado.

zeruel-tasks

Los conectores. Cada uno es un feature: se paga sólo el que se activa.
ShellTask +1 dep
Ejecuta un comando. Cancelable y con timeout. Si el comando imprime zeruel:rows=N, ese número entra en las métricas.
HttpTask +23 deps
Descarga en streaming por bloques de 64 KB, así un archivo de 2 GB no pasa por memoria. Las credenciales salen de variables de entorno.
PostgresSource / PostgresSink +53 deps
Lee y escribe con COPY, en streaming. El borrado previo va en la misma transacción que la carga: o queda todo, o no queda nada.
SnowflakeStatement +2 deps
Por la API REST, sin librerías nativas. Para volumen, el camino es staging en S3 y COPY INTO.

zeruel

La fachada: lo que se pone en el Cargo.toml de un pipeline.
pipeline(dag)
Arma el binario del pipeline: le da --describe y run sin que haya que escribir un CLI.
bundle()
Varios pipelines en un binario. Útil para agrupar los de un mismo dominio: comparten el ejecutable y bajan el disco que ocupan.
Error
Errores tipados en la superficie pública, así el pipeline no queda obligado a usar anyhow.

zeruel-cli

El binario zeruel: todo lo que se opera.
serve
El scheduler. Lee la cola, evalúa el cron y lanza los pipelines.
web
El panel: estado de los runs, métricas, cola, logs y el grafo. Sólo lee y encola.
mcp
Servidor MCP por stdio: deja que una IA consulte el estado y encole trabajo. Once herramientas.
servicio
Instalar, arrancar, parar y sacar el servicio de Windows. En Linux esto lo hace systemd.
gc
Poda por retención: 30 días de detalle por tarea, 1 año de runs, agregados mensuales para siempre. Corre solo, pero se puede forzar.
enqueue, backfill, sla, cola, status, list
Operación desde la terminal. Todos aceptan --json.

Como servicio

Son dos servicios, no uno. El scheduler y la web se instalan por separado porque el scheduler es lo que no puede caerse: reiniciar la web para cambiarle el puerto no tiene por qué interrumpir un ETL de dos horas.

Linux

sudo cp packaging/zeruel.service /etc/systemd/system/
sudo systemctl enable --now zeruel
journalctl -u zeruel -f

Windows

# como administrador
zeruel servicio instalar --nombre zeruel `
    --state "C:/zeruel/state" --pipelines "C:/zeruel/pipelines"

zeruel servicio instalar --nombre zeruel-web --modo web --puerto 9876 `
    --state "C:/zeruel/state" --pipelines "C:/zeruel/pipelines"

# el dia a dia pide los permisos solo
zeruel servicio arrancar --nombre zeruel
zeruel servicio estado   --nombre zeruel

Cada instancia corre bajo su propia cuenta aislada (NT SERVICE\zeruel), no como administrador, y sólo recibe permiso sobre su propio state. Dos instalaciones —desarrollo y producción— no pueden tocarse el estado entre sí.

Los dos al mismo state

El scheduler y la web tienen que apuntar al mismo --state y al mismo --pipelines. Con rutas distintas, la web lista DAGs que el scheduler no puede ejecutar, y el botón de ejecutar no hace nada.

Configuración

Gana el más específico:

flag de CLI  ›  variable de entorno  ›  zeruel.toml  ›  default
# zeruel.toml
[zeruel]
paralelo    = 4
ram_max     = "2G"
timeout_min = 60

[web]
token = "${ZERUEL_TOKEN}"   # el nombre, no el secreto

[entorno]
PGPASSWORD = "${PG_PASS}"   # lo heredan los pipelines

El archivo guarda el nombre de la variable, no su contenido, así que se puede versionar sin que el secreto entre al repositorio. Y una clave que no existe hace fallar el arranque diciendo cuál: un max_run mal escrito que se ignore en silencio deja el sistema con el default y a alguien convencido de que lo cambió.

Cuando algo falla

Un run terminó bien pero figura como fallido

Casi seguro hay dos bases en el directorio de estado: el pipeline se compiló contra una versión distinta de zeruel y escribe en un archivo que el scheduler no lee. Mirá si hay más de un .db en state/. Se arregla recompilando los pipelines y volviéndolos a copiar.

El botón de ejecutar no hace nada

La web y el scheduler están mirando directorios de pipelines distintos. En la lista de DAGs, los que tienen binario aparecen como desplegados; los otros vienen compilados y no se pueden ejecutar. Los dos comandos tienen que recibir el mismo --pipelines.

Hay items en cola con RAM de sobra

Es el control de admisión: no larga un run si su pico histórico no entra en lo que queda libre. Si el pico histórico está inflado por una corrida atípica, se corrige con un techo explícito (--ram-max).

Un run quedó en «corriendo» para siempre

El proceso murió sin poder cerrar su run — típicamente porque el supervisor lo mató antes de que terminara el apagado. Al arrancar, el scheduler rescata esos items y los devuelve a la cola. Si pasa seguido, subí el plazo del supervisor por encima de --gracia-secs.

«database is locked»

No debería pasar: la base abre con busy_timeout de 5 segundos y las escrituras son cortas. Si aparece, es señal de una transacción larga — reportalo con el log del run.
